Cat Wiki 架构审计：Gap Report

审计时间：2026-05-20 | 范围：SCHEMA.md vs 实际目录 + 用户路径合理性 + entity/concept边界

A. SCHEMA vs 实际差异

#差异严重度判定
A1preparation.md 不存在 — 6 处 wikilink 指向 404🔴 CRITICAL补文件（不是改SCHEMA）
A2breed-exotic.md 位置错误 — 在 concepts/acquisition/ 但应为 entities/（type=entity, tags含breed）🔴 CRITICAL移文件 → entities/
A3type: entity 误用 — 35 个 concepts/ 下文件使用 type: entity，但 SCHEMA 不定义此值。合法值：concept | breed | illness | care-guide | comparison | medication | homepage🟠 HIGH修 type（按实际语义重分类）
A4用药模块命名/结构偏离 SCHEMA — SCHEMA 定义顶层 medication.md → medication-hub.md / medication-kit.md / medication-admin-guide.md / medication-<name>.md。实际为 concepts/medication-guide/index.md + emergency-kit.md + safety.md，缺少 medication-admin-guide.md🟠 HIGH修 SCHEMA 对齐实现（实现更合理）
A5用药实体 frontmatter 字段名不匹配 — 22 个药物文件用 category: medication + drug_class/emergency_level，SCHEMA 要求 type: medication + medication_type/active_ingredient/administration/prescription🟠 HIGH修 SCHEMA 对齐实现，或统一 frontmatter
A6methods/ 和 templates/ 目录缺失 — SCHEMA 目录结构声明但实际不存在🟡 LOW可接受（暂不需要）或删 SCHEMA 条目
A7entities/ 下仅有 breeds + medications — SCHEMA 声称 entities 包含 “brands, hospitals, insurance products”，D2 记录”阶段一嵌入概念页”🟡 LOW现状符合 D2，后续扩展时建立
A8comparisons/ 仅 1 文件 — SCHEMA 树已展开但内容稀疏🟡 LOW无问题，按需增长

B. 用户路径痛点

B1. 🔴 新手路径 Stage 2 死胡同

index → newbie-guide → "查看完整接猫准备指南" → [[preparation]] → 404

6 个文件引用 [[preparation]]：newbie-guide, first-month, concepts/medical, concepts/insurance, concepts/safety, concepts/vaccine。这是新手引导的主要中断点。

B2. 🟡 老手路径 diet-staple 深度 >4 层

index → experienced → daily-care → diet → diet-staple → diet-staple-dry (5 clicks)

5 层导航。diet-staple 作为主食形态的分类枢纽有其存在价值，但子页面（dry/canned/freezedried/frozenraw/rawmeat/rawbones）只有 staple 页面能直接到达。对”我想了解干粮”的用户需要 5 次点击。

B3. 🟡 用药导航路径断裂

SCHEMA 设计 medication.md（根）→ medication-hub.md（索引入口）。实际不存在这两个文件。药品的实际入口是 concepts/medical.md 的子分类表 → concepts/medication-guide/index.md，路径合理但文件名与 SCHEMA 不匹配。

B4. 🟢 搜索路径

搜索框嵌入 index.md 正常工作（Quartz flexsearch）。潜在问题：药物文件使用 category: 而非 type: 可能不影响搜索索引（Quartz 主要索引 title + content），但影响内容分类过滤。

C. 导航深度 >4 层路径

路径层数是否合理
index → experienced → daily-care → diet → diet-staple → diet-staple-dry5可接受（diet-staple 是有价值的分组枢纽）。建议：experienced 页加”干粮/罐头”等快速锚点
index → experienced → daily-care → diet → diet-staple → diet-staple-*5同上，共 6 个子页
index → experienced → medical → illness → illness-flutd4合理
index → experienced → medical → medication-guide → ../../entities/medications/amoxicillin4合理（跨目录深度链接）

结论：仅 diet-staple-* 超过 4 层，但每个中间页面都是有效的 hub page（非空壳），不推荐扁平化。

D. Entity/Concept 分界线

当前状态

内容类型所在位置type 标记是否一致
品种 (breed-ragdoll, breed-british-shorthair)entities/type: breed ✅✅
品种 (breed-exotic)concepts/acquisition/type: entity ❌❌ 应移入 entities/，type 改为 breed
药品数据 (amoxicillin, doxycycline…)entities/medications/category: medication⚠️ 应使用 SCHEMA 的 type: medication
用药指南 (安全、药箱、索引入口)concepts/medication-guide/category: concept✅ 指南属于概念
疾病页 (illness-*.md)concepts/type: entity ❌❌ 应为 type: illness
保险 (insurance)concepts/type: entity⚠️ 阶段一嵌入概念，type 应为 concept
养育子页 (diet/hygiene 子页)concepts/type: entity ❌❌ 应为 care-guide

核心问题诊断

type: entity 在实现中被曲解为”叶子信息页”标记，而非 SCHEMA 定义的”离散可枚举实体”。这导致 entity/concept 边界完全模糊——用户无法从 type 字段区分”这是一个品种页”还是”这是一篇疾病文章”。

用户是否需要感知这条分界线？ 在当前阶段，直接导航不需要（所有页面通过 hub 页链接）。但 type 会影响：1) 搜索/过滤精度 2) 未来自动生成索引 3) 内容维护者理解文件定位。建议修复 type 值以支持这些下游用途。

E. 可扩展性评估

E1. breeds 扩容到 N=50

当前 entities/breed-*.md 扁平结构：2 个品种时没问题，50 个时 entities/ 目录下混合 breed + medications 会混乱。

建议：N>10 时建立 entities/breeds/ 子目录。当前暂不需要但 SCHEMA 应预留。

E2. Tag 系统

Content type tags (12) + life stage tags (4) + medication tags (8) + source tags (6) = 30 个标签。覆盖按生命阶段/品种/疾病类型的交叉筛选。

当前问题：life_stage frontmatter 仅在 first-month.md 设置了一次。实际内容页（diet/hygiene/illness）几乎全部未标注 life_stage。这意味着”筛选幼猫饮食”的查询无法通过标签实现。

E3. medication 模块

22 个药物页面 + 3 个指南页面。结构：entities/medications/ 按通用名存放是合理的（N=100 时仍可按首字母分文件夹）。药物之间的交叉引用（例如抗生素→慎用说明→肝肾药）尚未建立，目前纯线性列表。
